# خطة معالجة هشاشة اختبارات الواجهة (Flaky Tests) — تنفيذ 1-2-3

> خطة قابلة للتنفيذ في محادثة جديدة بالكامل، دون الاعتماد على سياق سابق.
> النسخة: 1.0 — تاريخ: أيلول 2026

---

## 1. الخلاصة التنفيذية

حزمة `frontend` تعاني من فشل متقطع (flaky) في اختبارات غير مستقرة زمنيًا تظهر **فقط** عند تشغيل
الحزمة الكاملة بالتوازي، وتختفي عند التشغيل منفردًا. التشخيص:

- **السبب الجذري H1 (مضخِّم)**: لا ضبط في `vitest.config.ts` لسقف المهلة/التوازي، و`DocumentForm.test.tsx`
  ملف ضخم (89 اختبارًا / ~1639 سطرًا) يعرض نموذجًا كاملًا تفاعليًا، تحت حمل 8 خيوط افتراضية.
- **السبب الجذري H2 (العلة الفعلية)**: تأكيدات متسابقة زمنيًا — قراءة `mock.calls[0]` فور النقر بلا
  `waitFor` (31 موضعًا في `DocumentForm.test.tsx`)، واختبارات تعتمد `debounce` (300ms) بسقف
  `waitFor` الافتراضي (1000ms).

الخطة تعدّل **الاختبارات فقط** (ولا تلمس كود المنتج) وتُنفَّذ بثلاث خطوات:

| الخطوة | المحتوى | دورها |
|--------|---------|-------|
| 1 | تقسية التأكيدات المتسابقة بـ `waitFor` ذي عدّادات دقيقة | **العلاج الحتمي** للهشاشة |
| 2 | ضبط `vitest.config.ts` (سقف مهلة + توازي مضبوط) | **حزام أمان** يمنع التقليم تحت الحمل |
| 3 | تقسيم `DocumentForm.test.tsx` إلى ملفات موضوعية | **صيانة بنيوية** للقراءة والتشغيل المستهدف (لا علاج للهشاشة) |

## 3. التشخيص الجذري (المحدد/المستبعد)

### 3.1 المؤكد — H2: أنماط هشة زمنيًا

**النمط «أ»: قراءة `mock.calls[N]` فور النقر بلا انتظار** (31 موضعًا في `DocumentForm.test.tsx`):

```
await user.click(screen.getByRole('button', { name: /حفظ/ }));
const [, payload] = vi.mocked(api.post).mock.calls[0] as [string, Record<string, unknown>];
expect(payload.annexType).toBe('تعديل');
```

إن تأخر معالج الحفظ لحلقة أحداث مخنوقة «لم تُطلق النقر المعلنة» — قراءة `calls[0]` تُرجع `undefined`
→ `payload` هو `undefined` → فشل. السباق حقيقي ويختفي منفردًا.

**المواضع القائمة** (قائمة تحريرية مُثبتة 31/31 بتاريخ المراجعة؛ يُعاد التحقق قبل التنفيذ عبر
`Select-String -Path "src\pages\DocumentForm.test.tsx" -Pattern "mock\.calls\["`):
31 موضعًا عند الأسطر: 286, 334, 361, 378, 422, 459, 518, 554, 567, 577, 588, 606, 634, 656, 672, 747,
809, 850, 990, 1027, 1094, 1147, 1230, 1249, 1305, 1353, 1386, 1410, 1456, 1523, 1569
(منها مواضع `api.put` عند 334, 588, 606, 1230).

**النمط «ب»: بحث مُرتد + سقف افتراضي**:
- `EntityRegistryReviewManagement.test.tsx:234-235`: `user.type` في حقل بحث يُنفَّذ خادميًا عبر
  الوسيلة المحلية `useDebounced(doSearch, 300)` في `EntityRegistryReviewManagement.tsx:269`
  (تعريفها `:1496` — وليست خطاف `useDebouncedValue` المشترك) ثم `findByRole` بسقف 1000ms
  الافتراضي. مُتحقق: الهشاشة انكسرت فعلًا عند هذه النقطة (البحث) لا عند تأكيد POST (المغلف بـ
  `waitFor` في `:253`).
- `AuditLogs.test.tsx:38`: **مُستبعد من التقسية** — حتمي لا هشّ: «نوم» فعلي `act` بطول 400ms يتجاوز
  دفّاق 300ms، وFIFO المواقِّت يضمن ترتيبه. يُصنَّف «لا تغيير مطلوب» (بطيء لكن صحيح).

**فئة «ج» مضافة (كانت تُغفل) — تأكيدات العدّ الفوري بعد النقر**: `expect(api.post).toHaveBeenCalledTimes(N)`
فور `user.click` بلا `waitFor` من نفس السباق (مثال موثق: `DocumentForm.test.tsx:448` و`:517`). القاعدة
العامة للخطوة 1: **كل قراءة/تأكيد على `api` أو `navigateMock` بعد فعل مستخدم يجب أن تتقدَّمه `waitFor`
بعدّاد دقيق** — لا تقتصر على صي‌غة `mock.calls[N]`.

**فئة «د» مضافة (مراجعة ثانية) — بوابات العرض المشتركة بسقف افتراضي**: `renderEdit`/`renderExecutedEdit`
(`DocumentForm.test.tsx:68` و`:75`) تنتظران أول ظهور عبر `findByText` **بسقف 1000ms الافتراضي**.
تحت حمل التوازي قد يتجاوز العرض الأول للنموذج الضخم هذا السقف، فينكسر ~40 اختبارًا عند البوابة
لا عند الحمولة. الإصلاح سطران فقط (سقف صريح على البوابتين) ويغطي كل المستدعين.

**مواقع مؤكدة خارج الملف الكبير (مراجعة ثانية — جرد شامل لكل `src`)**:
- `ExecutedStatusModal.test.tsx` (~150–161 و~235–239): `await user.click('حفظ الحالة')` ثم تأكيد
  فوري `toHaveBeenCalledWith`/`toHaveBeenCalledTimes(1)` بلا `waitFor` — **نفس العائلة، هدف تقسية**.
- `AppealFormModal.test.tsx:97-101`: **النمط المرجعي الصحيح أصلًا** — `await vi.waitFor(onSaved...)`
  (أثر لاحق) قبل قراءة `apiMock.post.mock.calls[0]` — **يُقتدى به ولا يُمسّ**.
- آمنة وتُستبعد: تأكيدات props المتزامنة (`onClose`/`onSaved`/`onPick` بعد نقر مُنتظَر —
  `TransferDocumentModal`/`FileAlertModal`/`DelegationFormModal`/`DelegationsCard`/`Login`/
  `PublicEntityPickerModal`)؛ اختبارات الخطافات بموقّتات وهمية (`useTimeout`/`useDebouncedValue`)؛
  `DocumentView.test.tsx` (مغلفة بـ `waitFor` أصلًا)؛ `UnifyNamesTab.test.tsx:139,187` (بعد نقر/
  `findBy` مُنتظَر — النداء متزامن في الـ effect)؛ `AuditLogs.test.tsx:38` (حتمي — §ب).

### 3.2 المؤكد — H1: ضغط التوازي بلا حزام

- `vitest.config.ts` (كامل): `environment: 'jsdom'` بلا `testTimeout` ولا `maxWorkers` ولا `pool`.
- سقف vitest 4 الافتراضي (مُتحقق من `node_modules/vitest/dist`): `testTimeout`=**5000ms**،
  `hookTimeout`=**10000ms**؛ سقف `waitFor`/`findBy` في Testing Library: **1000ms**.
- الافتراضي `pool: 'forks'` (عمال fork = عمليات فرعية) وعدد العمال = `availableParallelism` (لم
  يُثبت «8 خيوط»؛ الرقم حاسم الجهاز). `maxWorkers` مفتاح صحيح في Vitest 4 (لا `maxParallelWorkers`).
- `DocumentForm.test.tsx` وحده ~140–150 ثانية تشغيلًا منفردًا، و89 اختبارًا يعرضون نموذجًا ضخمًا.
  ومُتحقق: **لا `vi.useFakeTimers` في الملفين المستهدفين** → `waitFor` بالزمن الفعلي متوافق.

### 3.3 المستبعد (مُتحقق)

- **تلوث بين الملفات**: vitest يعزل كل ملف في مشغّل مستقل؛ أدوات المحاكاة داخل الملف
  (`vi.hoisted` + `vi.clearAllMocks` في `beforeEach`). لا علاقة عرضية بين الملفات.
- **انحدار منتج**: لا تغيير في `${frontend/src}` (خارج الاختبارات) — الرجوع إلى `git diff`.

## 5. الخطوة 1 — تقسية التأكيدات المتسابقة (العلاج الحتمي)

### 5.1 القاعدة المعتمدة

**كل قراءة لسجل نداءات mock بعد حدث UI يجب أن تتقدَّمها `waitFor` بعدّاد دقيق** — والعدّاد الدقيق
واجب لأن `waitFor` المجردة («استُدعيت النقطة» فحسب) تُخفي أخطاءً حقيقية (استدعاءات مكررة/زائدة).

**النمط المعتمد «أ»** (نداء واحد متوقع) — مع الإبقاء حرفيًا على مُحدد الزر الأصلي للاختبار
(مثلًا `/حفظ/` أو `/حفظ التعديلات/`؛ لا يُغيَّر أي مُحدد أثناء التقسية — تغيير المحدد يغيّر المعنى):

```ts
await user.click(screen.getByRole('button', { name: /حفظ/ }));

await waitFor(() => expect(api.post).toHaveBeenCalledTimes(1));
const [, payload] = vi.mocked(api.post).mock.calls[0] as [string, Record<string, unknown>];
expect(payload.annexType).toBe('تعديل');
```

**النمط المعتمد «ب»** (مواضع `api.put`): نفس الصيغة مع `api.put`.

**النمط المعتمد «ج»** (اختبارات الـ debounce): سقف صريح يسمح بمسار «كتابة + 300ms + عرض»:

```ts
await waitFor(() => expect(api.get).toHaveBeenCalledTimes(1), { timeout: 3000 });
```

**النمط المعتمد «د»** (بوابتا العرض المشتركتان — سطران يغطيان ~40 اختبارًا):

```ts
async function renderEdit(doc: DocumentResponse = mockDoc) {
  paramsMock.id = '1';
  (api.get as unknown as ReturnType<typeof vi.fn>).mockResolvedValue({ data: doc });
  render(<DocumentForm />);
  return screen.findByText('📂 وقوعات الملف', {}, { timeout: 5000 });
}
```

(نفس السقف الصريح على `renderExecutedEdit`.) لا يغيّر المعنى: مجرد مهلة انتظار أطول لأول ظهور.

### 5.2 حدود التعميم — لا تُقسَّى بالعمى

- بعض الاختبارات تتوقع نداءات متعددة (مثل إنشاء الملف ثم ملاحقه أو أنماط save مرتين). لكل موضع:
  1. اقرأ تكرار النداءات المتوقع من سلوك الاختبار أولًا.
  2. استخدم العدد الدقيق في `waitFor(expect(...).toHaveBeenCalledTimes(N))`.
  3. بعد التحقق، صِف التغيير في الـ commit على أنه «تقسية تأكيد زمني بلا تغيير سيمانتيكي» — وسيُثبت
     الركض الأخضر أن السيمانتيك لم تتغيّر (لو تغيّر معنى لانكسر الاختبار نفسه).
- الـ `waitFor` **غير مستوردة حاليًا** في `DocumentForm.test.tsx` (السطر 2 يستورد `{render, screen,
  within, fireEvent}` فقط) — التقسية تستلزم **إضافة `waitFor` إلى الاستيراد من
  `@testing-library/react`**. (مستوردة أصلًا في `EntityRegistryReviewManagement.test.tsx:2`.)
- شمل فئات «ب» و«ج» و«د» (§3.1): لا تُحصِ حصر `mock.calls[N]` فحسب؛ امسح الملف عن كل تأكيد
  زمني بلا وسيط (`rg` **غير متوفرة على هذا الجهاز** — استخدم `Select-String` الأصلية):
  `Select-String -Path "src\pages\DocumentForm.test.tsx" -Pattern "mock\.calls\[|toHaveBeenCalledTimes|navigateMock"`.

### 5.3 حزمة العمل القابلة للتطبيق خارج الملف الكبير

أهداف مؤكدة (لا تكتفِ بالمسح — نفّذ عليها النمط «أ» مباشرة):
- `src/components/ExecutedStatusModal.test.tsx` (~150–161 و~235–239).
- `src/pages/EntityRegistryReviewManagement.test.tsx:235` — سقف صريح على `findByRole`:
  `await screen.findByRole('button', { name: /وزارة التعليم/ }, { timeout: 3000 })`
  (أو `waitFor(api.get called)` قبلها — أيهما أنسب للسياق).

ثم مسح تأكيدي عام (بـ `Select-String`، لا `rg`):
`Select-String -Path "src\*.test.tsx","src\*\*.test.tsx" -Pattern "mock\.calls\[[0-9]+\]"` مع استثناء
الموثق آمنًا في §3.1 (النموذج المرجعي `AppealFormModal`، الـ props المتزامنة، ملفات الخطافات).

## 6. الخطوة 2 — ضبط `vitest.config.ts` (حزام الأمان)

### 6.1 التعديل المستهدف

`frontend/vitest.config.ts` — إضافة داخل كتلة `test`:

```ts
test: {
  globals: true,
  environment: 'jsdom',
  setupFiles: './src/test/setup.ts',
  css: false,
  include: ['src/**/*.test.{ts,tsx}'],
  testTimeout: 15_000,   // سقف حقيقي للنموذج الضخم بدل 5000 الافتراضي
  hookTimeout: 15_000,   // مطابقة للسماح بإعداد ثقيل داخل hooks (الافتراضي 10000)
  maxWorkers: 4,         // يخفف التنافس على السعة دون شلّ التسريع (مفتاح صحيح في Vitest 4)
}
```

ملاحظة قابلية النقل: `maxWorkers` يقبل نسبة (`'50%'`) — بديل صالح على أجهزة غير معروفة النوى،
ويوجد تجاوز بيئي `VITEST_MAX_WORKERS` بلا تعديل ملف. القيمة `4` معتمدة على جهاز التطوير الحالي.

**مبرر**: الخطوة 1 تجعل الاختبارات صحيحة تحت أي حمل؛ الخطوة 2 تمنح حدًّا أدنى مضمونًا حتى لا يُقصّ
اختبار تفاعلي ثقيل عند 5 ثوانٍ عند هبوط النظام.

### 6.2 (اختياري) سكربت CI حاسم

أضف في `package.json` ضمن `scripts`:

```json
"test:ci": "vitest run --maxWorkers=4 --pool=forks"
```

`pool: 'forks'` يعزل العمليات بإحكام أمان أعلى على Windows (العزل بالعمليات لا الخيوط) — يُستخدم
فقط في CI، ويبقى الأمر المعتمد محليًا حسب `AGENTS.md` هو `npx vitest run` بلا وسائط.

### 6.3 ممنوع

- **لا** `retry` عام على مستوى الحزمة: يُخفي العلة ويُبقيها حية. مقبول مؤقتًا فقط (وبقيد متتبّع)
  لو اضطُر لأمر يوقف الإصدار — تُوثَّق في الـ commit وتبقى المهمة مفتوحة حتى تُزال.
- **لا** زيادة سقف بلا مبرر لكل ملف: السقف العام كفيل بعد الخطوة 1.

## 7. الخطوة 3 — تقسيم `DocumentForm.test.tsx` (صيانة بنيوية)

### 7.1 المبدأ

التقسيم **لا يعالج الهشاشة** (وثّق ذلك في commit/مقر)، لكنه يقلّص الملف من ~1639 سطرًا، ويسمح
بتشغيل مستهدف (مثل `vitest run DocumentForm.annex.test.tsx`)، ويقصّر زمن الملف الواحد — فهو دين
صيانة مستقل الهدف. **تنبيه دقيق**: التقسيم لا يخفّض إجمالي عمل CPU (بل يزيده قليلًا بكلفة تحميل
الوحدة لكل ملف) وقد يرفع ذروة التوازي (ملفات أكثر = عمال مشغولة أكثر)؛ مكسبه القراءة والاستهداف
لا تخفيف الحمل.

### 7.2 محاور التقسيم المقترحة (تُؤكَّد بقراءة أسماء الاختبارات أولًا)

| الملف الجديد | الموضوع | نطاق الأسطر التقريبي (يُتحقق) |
|--------------|---------|-------------------------------|
| `DocumentForm.entityParties.test.tsx` | ربط الأطراف بسجل الجهات، نوافذ الاختيار، طلاب التنفيذ الاعتباريون، الوكيل القانوني | ~92–183 |
| `DocumentForm.annexAndLayout.test.tsx` | ملحق العقد، التخطيط/العرض، افتراضيات «مصرفي»، أسماء الحقول والأعمدة | ~184–339 |
| `DocumentForm.payloadAndFields.test.tsx` | تعبئة المحافظة/الفرع، التواريخ وحقول القيد، المالكون/الكفلاء/الضمانات، الحمولات عند الحفظ | ~340–1639 (يُقسم ثنائيًا إن تجاوز ~500 سطرًا) |

قاعدة التقسيم: **كل ملف ≤ ~500 سطر + مجموعة حماية واحدة**؛ تُستخرج وحدات إضافية إن لزم.

### 7.3 نمط الملفات المشارِكة (إلزامي للسلامة)

`vi.hoisted` و`vi.mock` **مُهرّبان لكل ملف ولا يُمرَّران بالاستيراد**. لذلك كل ملف جديد يحمل كتلة
الإعداد نفسها (حوالي 20 سطرًا) — تكرار مقصود للعزل (وثّقه في تعليق أعلى شكل الملف):

```ts
// ملف اختبار موزّع من DocumentForm.test.tsx (سابقًا سطر 1–38).
// vi.hoisted/vi.mock تُكرَّر عمدًا في كل ملف موزَّع — vitest يعزل الملفات وكذا تقلبات المحاكاة.
// كتلة الاستيراد كاملة إلزامية (انسخها من المصدر ولا تختصرها — أي نقص يكسر tsc/oxlint):
import { describe, it, expect, vi, beforeEach } from 'vitest';
import { render, screen, within, fireEvent, waitFor } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import type { ReactNode } from 'react';
import DocumentForm from './DocumentForm';
import { api } from '../api/client';
```

## 8. بروتوكول التحقق الإلزامي (بعد كل خطوة وقبل إعلان إنجازها)

أوامر تشغيل من `frontend/`:

```bash
npx oxlint src
npx tsc -b
npx vitest run            # الحزمة الكاملة — مطلوبة مرتين متتاليتين خضراوين
npm run build
```

**دليل الحتمية الإضافي** (أقوى دليل أن الاختبارات كفّت عن الاعتماد على الحمل):
```bash
npx vitest run --maxWorkers=1   # يثبت الخضرة حتى بلا أي توازٍ (أثقل اتصال)
```

قواعد التحقق:
- الحزمة الكاملة خضراء **مرتين متتاليتين** بعد كل خطوة (لا تكفي مرة واحدة لملف معروف الهشاشة).
- الخضرة عند `--maxWorkers=1` **وبـ** التوازي الافتراضي معًا.
- صفر تحذيرات/أخطاء في `oxlint`، نظيف `tsc -b`، نجاح `npm run build`.
- **صفر تغيير في كود المنتج ضمن نطاق المهمة**: بعد الخطوة 0 (§4) يجب أن يظهر `git diff` فقط ملفات
  الاختبارات + `vitest.config.ts` (+ `package.json` إن أُضيف السكربت).
