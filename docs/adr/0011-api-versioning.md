# ADR-0011 — سياسة إصدار `API` والإهمال

- **الحالة:** معتمد (سياسة ملزمة) — **آلية الإصدار وقت التشغيل مؤجلة بقرار موثّق**.
- **التاريخ:** 2026-11-25.
- **المرجع:** `P4-04` / `P4-04b` — [`docs/API_VERSIONING.md`](../API_VERSIONING.md)،
  `docs/audit/54-p4-04-openapi-contract-20261117.md`،
  `docs/audit/97-p4-04b-openapi-response-schemas-20261122.md`، `docs/audit/249…251`.
- **يرتبط بـ:** [`0003-idempotency-all-writes.md`](0003-idempotency-all-writes.md) (عقود
  الكتابة)، [`0008-api-error-contract.md`](0008-api-error-contract.md) (عقد الخطأ جزء من
  السطح العام).

## 1. السياق

`P4-04` ثبّت أساس العقد: `operationId = Controller_Action`، ولقطة `OpenAPI` مُطبَّعة في
`docs/openapi/docgen-v1.json` يتحقق منها `OpenApiContractTests`، وعميل `TS` مولَّد في
`frontend/src/api/generated.ts` يحرسه `CI` ضد الانحراف. لكن السطح بقي **بلا آلية إصدار**:
كل المسارات `/api/…` (245 عملية في `2026-11-25`) بلا بادئة، و`info.version = "v1"` هو
إصدار **وثيقة العقد** لا إصدار تعايش وقت التشغيل.

هذا يخلق خطرين: (1) تغيير كاسر يمرّ بلا نسخة تعايش فيتوقف مستهلك فجأة، (2) إهمال عملية
بلا سجل معلن فيُحذف بلا نافذة ترحيل. المطلوب الآن سياسة صريحة **قبل** الآلية، لأن الآلية
بذاتها تغيير واسع (كل المسارات + عنوان القاعدة + إعادة توليد العميل) ولا تُنفَّذ استباقًا.

## 2. القرار

1. **السطح يبقى غير مُصدَّر** (`/api/…`) في هذا الإصدار. لا بادئة `/api/v1` ولا ترويسة
   `Accept-Version`، ولا تغيير في المسارات أو `DTO` أو شكل الاستجابة.
2. **لا تغيير كاسر بلا إصدار.** ما دامت آلية التعايش غير منفَّذة، التغيير الكاسر **ممنوع**؛
   المسموح هو الإضافي فقط (مسار/حقل اختياري/مخطط/عملية جديدة).
3. **عند التفعيل، الافتراضي هو بادئة المسار `/api/v1`** لأنها ظاهرة في السجلات/الكاش/
   البوابات وتسمح بتشغيل نسختين بالتوجيه وحده.
4. **سياسة الإهمال إلزامية فورًا:** إعلان ← تشغيل مزدوج ← إزالة، بنافذة لا تقل عن **90
   يومًا** ودورة إصدار كاملة (الأطول)، عبر سجل `docs/openapi/deprecations.json` الذي
   يحمل `operationId`/`deprecatedSince`/`removalVersion` أو `removalDate`/`replacement`.
5. **الإنفاذ آلي قدر الإمكان:** `ApiVersioningPolicyTests` يفرض تطابق اسم اللقطة مع
   `info.version`، ونمط `operationId` وفرادته، ووجود السياسة و`ADR-0011` وربطهما من فهرس
   الوثائق، ومطابقة سجل الإهمال للمخطط وللقطة، ووسم كل عملية `deprecated` في اللقطة.
6. **تفعيل الآلية قرار مالك صريح** لأنه يمسّ كل مسار + `frontend/src/api/client.ts` +
   إعادة توليد `generated.ts`، ويحتاج `staging` لتشغيل نسختين (`P5-04`). حتى ذلك الحين
   يبقى الدين معلنًا في `PERFECTION_ROADMAP.md` (§`P4-04`).

## 3. البدائل المرفوضة

| البديل | لماذا رُفض |
|---|---|
| **البقاء بلا إصدار للأبد** | يمنع أي تطور كاسر مستقبلًا ويجعل الإهمال بلا نافذة؛ لا يجيب سؤال «كيف نُزيل عملية؟» |
| **`Accept-Version` الآن** | وسيط تفاوض + `Vary` + تعقيد كاش + لا يظهر في المسار؛ لا يشتري شيئًا والمستهلك الوحيد هو `SPA` المضمَّن |
| **`Asp.Versioning`/`[ApiVersion]` الآن** | اعتمادية جديدة + تعديل كل متحكم (245 عملية) بلا مستهلك خارجي يستدعيها؛ القرار الاستباقي يخالف «لا اعتمادية بلا حاجة» |
| **إصدار بالتاريخ (date-based)** | لا يعبّر عن التوافق الدلالي، ويصعّب على العميل معرفة النسخة المدعومة |
| **إصدار لكل متحكم** | يجزّئ السطح ويضاعف مصفوفات الاختبار والتوثيق بلا مكسب للمستهلك |
| **الاعتماد على `generated.ts` بدل سياسة إصدار** | يكشف الكسر **بعد** الدمج/النشر لا قبله، ولا يوفّر نافذة ترحيل |
| **فحص يدوي في المراجعة بدل حارس** | لا يمنع النسيان؛ أثبتت المراحل السابقة أن الحراس الآليين وحدهم يمنعون الانحراف الصامت |

## 4. النتائج

- **إيجابًا:** قاعدة واضحة الآن (لا كاسر بلا إصدار، نافذة إهمال 90 يومًا، سجل موحّد)،
  وحراس آليون يمنعون إهمالًا غير موثّق أو انحراف علامة الإصدار قبل النشر.
- **سلبًا/دينًا معلنًا:** آلية التعايش وقت التشغيل غير موجودة؛ أي حاجة ملحّة لتغيير كاسر
  تتطلب أولًا تنفيذ الآلية (عمل مستقل، قرار مالك + `staging`) — لا يُتجاوز بالقاعدة.
- **لا أثر على السلوك:** لم يتغير مسار ولا `DTO` ولا استجابة ولا هجرة في هذا القرار.

## 5. المالك والاعتمادية

- **المالك:** مالك المشروع (تفعيل الإصدار الأول ونافذة إهمال أقصر من 90 يومًا).
- **الاعتمادية:** `staging`/`canary` (`P5-04`) لتشغيل نسختين فعليًا، وإحلال
  `types/document.ts` المتبقي بالعميل المولَّد (`P6-06`) كي لا يتضاعف أثر الإصدار.
