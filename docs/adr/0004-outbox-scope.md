# ADR-0004 — نطاق الـOutbox: `HeadAlertOutbox` هو الآلية المعتمدة حاليًا

- **الحالة:** معتمد (`P0-05`).
- **التاريخ:** 2026-11-14.
- **السياق:** `docs/PERFECTION_ROADMAP.md` §4 `P0-05`، و`docs/adr/0003-idempotency-all-writes.md`.
- **القرار:** لا يُضاف جدول Outbox عام جديد الآن. `HeadAlertOutbox` القائم هو
  الـOutbox المعتمد لكل أثر جانبي حالي، وأي أثر جانبي جديد يمرّ عبره أو عبر
  `adapter` يضيف نوعًا/معالجًا فوقه. يُعاد تقييم التعميم عند ظهور منتج ثانٍ
  مستقل (خارج تنبيهات الرأس).

## 1. الواقع الحالي

`HeadAlertOutbox` ليس جدول تنبيهات بسيطًا؛ هو Outbox ناضج:

- `Enqueue` داخل معاملة العملية نفسها (نفس `DbContext`) — لا أثر جانبي بعد commit.
- حجز بـ`lease`: `LockedUntil` + `LockedBy`، واستعادة الصفوف المنتهية.
- إعادة محاولة بتراجع: `Attempts`، `NextAttemptAt`، `LastError`.
- حالات صريحة: `pending/processing/processed/skipped/failed`.
- مشغّل خلفي واحد (`HeadAlertOutboxDispatcher`) مع صيانة دورية.
- فحص صحة (`HeadAlertOutboxHealth`: pending/oldest/failed) واختبارات
  retry/idempotency/stale events.
- مراقبة `outbox lag` موجودة في واجهة المتجر، وربطها بـ`/readyz` بند `P5-03`.

## 2. لماذا لا جدول عام الآن؟

- **لا منتج ثانٍ:** الآثار الجانبية الفعلية كلها تنبيهات رأس. جدول عام بلا
  منتج = بنية غير مستخدمة وتكلفة صيانة ومخاطر هجرة بلا فائدة سلوكية.
- **تكلفة الترحيل:** استبدال `HeadAlertOutbox` بجدول عام يتطلب ترحيل بيانات
  حية، ومشغّلًا/معالجًا لكل نوع، وإعادة كتابة اختبارات التنبيهات — تغيير واسع
  عالي المخاطر على نظام حي، بينما `DoD` الجوهري محقق أصلًا.
- **مبدأ التجريد المتأخر:** التعميم يُبنى عند الحاجة الثانية الحقيقية، لا قبلها.

## 3. الالتزامات

1. أي أثر جانبي جديد **داخل معاملة العملية**، لا `Task.Run`/إرسال مباشر بعد commit.
2. إن كان الأثر تنبيه رأس → `IHeadAlertOutbox` القائم.
3. إن كان نوعًا مختلفًا → `adapter`/نوع جديد فوق نفس البنية مع معالج idempotent،
   أو قرار ADR جديد بالتعميم إذا تعددت الأنواع.
4. `outbox lag` و`/readyz` ضمن `P5-03`؛ لا يُغلق `P5-03` قبل ربط العتبة والتنبيه.

## 4. معايير إعادة التقييم (Triggers)

- ظهور منتج ثانٍ مستقل عن تنبيهات الرأس (بريد، Webhook، تقارير، مزامنة خارجية).
- الحاجة إلى `IOutboxHandler` registry بمعالجات متعددة قابلة للتسجيل من موديولات.
- الحاجة إلى معالجة موزّعة/توسّع أفقي يتجاوز قفل المشغّل الواحد الحالي.
- تجاوز `outbox lag` حدود SLO مع نمو الحجم.

## 5. البدائل المرفوضة

- **تعميم كامل الآن:** مخاطرة ترحيل عالية بلا منتج ثانٍ، وتغيير سلوك تنبيهات حي.
- **جدول عام فارغ + مشغّل بلا معالج:** تجريد مسبق يزيد السطح بلا قيمة، ويصعّب
  المراجعة والتشغيل.

## 6. الأثر

- لا هجرة ولا تغيير مخطط في هذا القرار.
- `P0-05` يُغلق بقرار موثّق، و`P5-03` يبقى مسؤولًا عن ربط lag بـ`/readyz`.
- أي عمل مستقبلي على Outbox يبدأ من هذا الـADR لا من افتراض جدول عام.
