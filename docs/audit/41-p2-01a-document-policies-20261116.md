## 1. البنية المنفّذة

**في `Application` (بوابة قراءة ضيقة):**

- `IDocumentAccessReader` + `DocumentAccessReader`: ثلاثة أسئلة فقط —
  إسقاط الوصول الخفيف (F-01، خمسة حقول)، وهل للمستند إحالة سارية، وهل المستخدم متابع
  مُسند. لا `DbContext` ولا مستودع كامل في طبقة السياسة.
- التسجيل في `AddApplication`.

**في `Api/Authorization/Documents`:**

| الملف | الدور |
|---|---|
| `DocumentAction` | تسع عمليات: `Read`, `ReadOrFollow`, `Edit`, `ChangeStatus`, `Delete`, `Restore`, `Rotate`, `ManageActions`, `Transfer`. |
| `DocumentAccessRequirement` + `DocumentAccessContext` | المتطلب + مورد التقييم (الإسقاط + مهلة الطلب). |
| `DocumentAccessHandler` | النقل الحرفي لقاعدة `CanAccessAsync` السابقة + قدرة كل عملية: مدير/مشرف يريان الكل بلا كتابة؛ المحامي ملكه؛ الرئيس فرعه + استثناء الإحالة؛ رئيس الشعبة شعبته؛ `ReadOrFollow` تضيف متابع الاستئناف. |
| `UserCapability` + `IUserCapabilities`/`UserCapabilities` | جسر القدرات غير الموردية (تعقيم العدّاد/أعمدة التصدير/فلتر المحامي) إلى الكتالوج المركزي، بأسماء مطابقة لدواله. |
| `IDocumentAuthorization`/`DocumentAuthorization` | نقطة واحدة للمتحكم: `AuthorizeAsync(id/document, action)`، `Has(capability)`، `ResolveListScope`. |
| `DocumentAuthorizationSetup` | تسجيل الخدمات والمعالج في `DI`. |

**في المتحكم:** حُذفت كل الخصائص الدورّية (`Role`, `HasFullAccess`, `CanEdit`, …,)
و`CanAccessAsync`/`CanAccessOrFollowAsync`/`RequireOwnerScope`. بقي:

```csharp
var denied = await RequireDocumentAccessAsync(id, DocumentAction.Delete, ct);
if (denied is not null) return denied;
```

## 3. تطبيع حالة حدّية (مقصود وموثّق)

سابقًا كان بعض مسارات الكتابة يفحص القدرة **قبل** تحميل المستند، فطلب على معرّف
**غير موجود** من دور بلا قدرة كتابة يُرَدّ `403`. الآن يُحلّ المورد أولًا
(`ADR-0007`): المفقود ⇒ `404` لكل الأدوار، والموجود خارج النطاق/القدرة ⇒ `403`.
لا اختبار قائم كان يعتمد على `403` للمفقود (تحقق استقصائي)، والمصفوفة الجديدة تثبت
الترتيب. الفائدة الأمنية: لا يُكشف شيء إضافي (المعرّف مُدخَل من العميل)، والدلالة
صارت موحّدة عبر كل الأفعال.

## 4. حراسة بنيوية وتحقق سلبي

**حارس جديد** (`DocumentsControllerAuthorizationGuardTests`): فحص نصّي على مصدر
المتحكم (مع تجاهل التعليقات) يمنع `RolePermissions` و`GetRoleEnum` — أي قرار دورّي
مباشر عائد. فيه:

- تحقق أن الملف موجود وأن عدد أسطر الكود > 100 (منع خضرة كاذبة عند مسار خاطئ).
- **تحكم إيجابي**: المنقّح يرى المخالفة في الكود لا في التعليق.

| الحقن المؤقت | النتيجة المرصودة | أُعيد؟ |
|---|---|---|
| حذف فحص الفرع من `HasScopeAccessAsync` | فشل خليتا العبور بين الفروع فقط (`Head` بملف شعبة في فرع آخر بإحالة، و`SubHead` بفرع آخر) — 30/32 ناجحة | نعم |
| إضافة `RolePermissions.HasFullAccess` إلى المتحكم | فشل حارس المتحكم وحده وسمّى السطر؛ بقي التحكم الإيجابي أخضر | نعم |

- **كتابة أخف:** مسارات الحالة/الحذف/النقل/الإجراءات/المتدخلات لم تعد تحمّل
  `DocumentResponse` الثقيل (~20 `Include`) لفحص الوصول؛ تكفي قراءة الإسقاط الخفيف.

- **الفشل مغلق:** قدرة أو عملية بلا ربط صريح ترمي/ترفض، ولا تُمنح افتراضيًا.

## 7. الحدود (ما لم يُنجز)

- **`P2-01b`**: البوابة (`PortalController`) وسجل الجهات (`EntityScopeRequirement`) —
  ما زالت تفحص `RolePermissions` في المتحكمات.
- **`P2-01c`**: المراجعات/المراسلات/التنفيذ/الإحصاءات + حارس «كل أكشن له متطلب أو
  استثناء موثّق» على كل المتحكمات. حتى ذلك الحين لا يمكن ادّعاء إغلاق الفشل المفتوح
  على مستوى التطبيق كله.
- **جسر القدرات ليس سياسة موردية**: `UserCapability` يفوّض إلى الكتالوج المركزي؛
  المتطلبات الموردية الحقيقية هي `DocumentAccessRequirement`. أي قدرة جديدة تُضاف
  إلى الكتالوج + مصفوفة `P2-02g` + الجسر، وإلا يفشل أحد الاختبارين.
- شروط الملكية داخل خدمات الإنابة/الاستئناف تبقى كما هي (دفاع عميق، `P2-02e`).
