## 2. ما نُفِّذ والنتائج

### 2.1 الهجرات ورفض الإقلاع (`AutoMigrate=false`)

- القاعدة كانت على **8 هجرات**، والناقصة: `20261127105840_W1_DepositExecutedBackfill`
  (هجرة بيانات فقط — «سبق تنفيذ الإيداع»).
- تشغيل التطبيق قبل التطبيق: **رفض الإقلاع** برسالة صريحة تسمّي الهجرة الناقصة وأمر
  `dotnet ef database update --context DocGeneratorPostgresDbContext` — السلوك الإنتاجي المقصود.
- تطبيق الهجرة عبر Design-Time (`POSTGRES_CONNECTION`) نجح، و`Done.`؛ أصبحت **9 هجرات**.

### 2.2 الإقلاع في `Production`

- `ASPNETCORE_ENVIRONMENT=Production`، `Database:AutoMigrate=false`،
  `DataProtection:PersistToDatabase=true`، `AllowedHosts` صريح، `HSTS`/`HttpsRedirection` مفعّلان،
  `CspReportOnly=false`، `Swagger=false`، وTLS محلي بشهادة اختبار.
- النتيجة: **`/readyz` = 200** و**`/healthz` = Healthy**.
- `DataProtectionKeys` بقيت **صفًا واحدًا** بعد الإقلاع (قُرئت المفاتيح المخزنة ولم يُولَّد مفتاح جديد).
- تحذير متوقع: `Security:KnownProxies` فارغ مع `TlsTerminatedByApp=true` (مقبول في هذا الاختبار؛
  في النشر خلف بروكسي تُضبط العناوين أو يُبقى إنهاء TLS في التطبيق).

### 2.3 نسخ احتياطي واستعادة (Drill)

1. `pg_dump` (أدوات `PostgreSQL 17.7` محمولة) بصيغة `plain` لمخطط `public` فقط:
   0.18MB، وبصمة `SHA-256` مسجّلة في سجل التشغيل.
2. إنشاء قاعدة مؤقتة `docgen_restore_w3a`، ثم `CREATE EXTENSION pg_trgm` (لأن تفريغ `public`
   لا يحمل تعريف الامتداد)، ثم تطبيق الملف بعد حذف سطر `CREATE SCHEMA public;`.
3. التحقق بعد الاستعادة: **52 جدولًا، 9 هجرات، 4 مستخدمين، 64 سجل تدقيق، 1 مفتاح
   Data Protection، 0 مستند** — مطابق للمصدر.
4. **حذف القاعدة المؤقتة** (`dropdb --force`) والتأكد من عدم بقائها.

**ملاحظات مستخلصة:**

- في `pg_dump --schema=public` لا يأتي `CREATE EXTENSION pg_trgm`؛ يجب إنشاؤه قبل الاستعادة
  (أو تفريغ المخططات كاملة مع استثناء مخططات `Supabase` الإدارية). أخطاء الاستعادة الأولى كانت
  من مخططات `vault/auth` الداخلية، لا من جداول التطبيق.
- الاستعادة إلى قاعدة جديدة تحتاج تجاوز `CREATE SCHEMA public;` (موجود مسبقًا) — إما بحذف
  المخطط قبل الاستعادة أو باستخدام قائمة `TOC` مفلترة.
- `pg_restore -L` مع ملف قائمة بولّدته PowerShell فشل (`input file is too short`)؛ الحل العملي
  الموثّق أعلاه هو تفريغ `plain` وتطبيقه بـ`psql` بعد الفلترة.

## 3. قائمة تحقق `W3b` (الخادم الخاص)

1. **إصدار `PostgreSQL`** (15+؛ يفضَّل 16/17) وتوفر امتداد **`pg_trgm`** (بدونه هجرة `P3-02` تفشل).
2. **تطبيق الهجرات التسع** بالترتيب قبل النشر:
   `dotnet ef database update --context DocGeneratorPostgresDbContext`، ثم التحقق من
   `__EFMigrationsHistory` = 9 صفوف، ومن أن `AutoMigrate=false` يُقلع بنجاح.
3. **النسخ الاحتياطي:** جدولة `pg_dump` (Custom/Plain) + نسخ المزوّد/WAL إن توفرت؛
   اختبار استعادة دوري (نفس خطوات §2.3) مع التحقق من الأعداد ثم حذف قاعدة الاختبار.
4. **الأمان الإنتاجي:** `AllowedHosts` للنطاق الفعلي، `HSTS`/`HttpsRedirection`، `CspReportOnly=false`،
   `Swagger=false`، و`KnownProxies` أو `TlsTerminatedByApp` حسب طوبولوجيا الخادم.
5. **الأسرار:** `DATABASE_URL`، `Jwt__Secret` (≥32 بايت)، `Bootstrap__AdminPassword`، ومفتاح تشفير
   الأرشيف — في **مدير أسرار الخادم**، لا في المستودع.
6. **أرشيف التدقيق:** مجلد محمي مشفّر + بصمات تحقق، ضمن النسخ الاحتياطي، وحذف بعد 5 سنوات
   (أول تشغيل تجربة جافة).
7. **تدوير المفاتيح الحالية** (`Render` وقاعدة الاختبار) بعد إغلاق `W3a`، وتحديث `DATABASE_URL`
   في `Render` في نفس الخطوة إن بقيت الخدمة.
