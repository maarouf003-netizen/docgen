# `RF-019` — تدقيق إلحاق-فقط قاعديًا + إجراء تنقية موثق (`SEC-008` ← `BQ-023`)

> الفرع: `refactor/RF-019-appendonly` (من رأس `refactor/RF-013-timestamps` التراكمي).
> الحالة: موجز مكتوب (Step 2) — بانتظار التنفيذ والتحقق.
> **تنبيه قاعدة 5**: الهجرتان تُكتَبان ولا تُطبَّقان (`dotnet ef database update` محظور)؛ نصا `SQL`
> في `docs/audit/migrations/`؛ ثم STOP لاعتماد صريح منفصل قبل أي تطبيق.
> القرارات المعتمدة لهذه الوحدة (جلسة `RF-019`): احتفاظ **سنتان** + التنقية
> **مشغّل النشر فقط** (`runbook` بلا زر) + منع **`UPDATE` و`DELETE`** معًا.

## Objective

سجل التدقيق إلحاق-فقط على مستوى القاعدة: أي تعديل أو حذف لصف في `AuditLogs`
أو `DocumentFieldChanges` — عبر التطبيق أو مباشرةً — مرفوض قاعديًا بخطأ صريح،
فيُغلَق تهديد `T-4` (مميز داخلي يمحو أثره). والتنقية الوحيدة المسموحة إجراء
تشغيلي موثق بيد مشغّل النشر حصرًا بعد نسخة واعتماد.

## Current problem

الحماية برمجية فقط (`SEC-008`): لا كتابة عبر `API` (`AuditLogsController` بلا
أي `HttpPost/Put/Delete` — تحققت) لكن `Repository<T>.Update/Remove` موروثة في
`AuditLogRepository` ولا منع قاعدي — أي وصول مباشر للقاعدة (أو كود مستقبلي)
يعدّل/يحذف بلا عائق. والكاتب `AuditLogger.cs:15-79` إدخال فقط أصلًا.

## Evidence (أُعيدت قراءتها في Step-1 على هذا الفرع وما زالت مطابقة)

- `AuditLogsController.cs` — صفر `HttpPost/Put/Delete` (بحث سلبي — تحققت).
- `AuditLogger.cs:15-79` — `Add` فقط (`LogAsync`/`LogManyAsync`/`LogDocumentChangeAsync`).
- صفر استدعاء `AuditLogs.(Remove|Update)` و`DocumentFieldChanges.(Remove|Update)`
  في `src` و`tests` (بحث سلبي — تحققت) — فالمنع لا يكسر أي مسار قائم.
- الجداول: `AuditLogs` (`AuditLogConfiguration.cs:12`) و`DocumentFieldChanges`
  (`DocumentFieldChangeConfiguration.cs:12`)؛ تتالي `DocumentFieldChange→AuditLog`
  لا يُطلَق عمليًا (حذف الأب محظور أصلًا بعد المنع).

## Files affected

- هجرتان جديدتان (مولّدتان بـ`dotnet ef`, غير مطبقتين) + لقطتان + نصا `SQL`:
  `SQLite` (4 مشغّلات `RAISE(ABORT)`) + `Postgres` (دالة `plpgsql` + 4 مشغّلات).
- اختبار `RF019AppendOnlyTests.cs` (خلفي — عبر `ApiFactory` المهاجَرة).
- `RUN_GUIDE.md` (إجراء التنقية التشغيلي حيث يجده المشغّل).
- لا كود مصدري إطلاقًا (الكتابة إلحاقية أصلًا — المنع قاعدي خالص).
- لا غير.

## Business behavior affected

مرفوض جديد مقصود ومعتمد (`BQ-023`): أي `UPDATE`/`DELETE` على الجدولين —
ولو مباشرةً — يفشل بخطأ قاعدي صريح. مسارات التطبيق العادية (إدخال + قراءة)
كما هي تمامًا.

## Security impact

إغلاق `T-4` على مستوى القاعدة (محو/تزوير السجل)؛ لا توسعة سطح (بلا نقاط جديدة).

## Database impact

**NEEDS-MIGRATION** (تحليل قاعدة 5 أدناه). مشغّلات منع فقط — لا تحويل بيانات،
لا مساس بالصفوف القائمة.

## API impact

none — نفس العقود؛ لا نقاط جديدة (التنقية تشغيلية خارج التطبيق عمدًا).

## Test strategy

1. إظهار (يفشل قبل الإصلاح): `UPDATE`/`DELETE` مباشر على `AuditLogs` و
   `DocumentFieldChanges` في قاعدة `ApiFactory` المهاجَرة → اليوم ينجح (الثغرة)،
   وبعد المنع يفشل `DbUpdateException`.
2. توصيف (يخضر قبل/بعد): `INSERT` تدقيق ما زال يعمل (دخول + إنشاء ملف يُدقَّقان).
3. الكاملة خلفية على قواعد معزولة (الواجهة لم تُمسّ).

## Rollback strategy

عكس الهجرة (`Down` يسقط المشغّلات/الدالة — آمن، بلا فقدان) + حذف ملفي الهجرة +
إعادة اللقطتين. القاعدة الحية لا تُمسّ حتى الاعتماد المنفصل. ملاحظة: التراجع
يعيد الحالة «قابل للكتابة تقنيًا» — يُوثَّق كتراجع طارئ بانكشاف معلوم.

## Type / Dependencies

**NEEDS-MIGRATION** (SQLite + Postgres — مشغّلات فقط). تعتمد `RF-001`.
`BQ-023` مبتوت (منع قاعدي + تنقية موثقة بصلاحية محددة).

## تحليلات الهجرة (قاعدة 5)

- **الهجرة**: 4 مشغّلات `BEFORE UPDATE/DELETE` على `AuditLogs` و
  `DocumentFieldChanges` (كل عملية على حدة لرسالة أدق) — `SQLite`: `RAISE(ABORT)`
  برسالة عربية؛ `Postgres`: دالة `plpgsql` واحدة (`RAISE EXCEPTION` مع `TG_OP`
  واسم الجدول) + 4 مشغّلات مربوطة بها.
- **الأثر**: فحص عند الكتابة الممنوعة فقط — `INSERT`/`SELECT` بلا أي كلفة
  إضافية؛ لا قفل، لا تحويل صفوف. الصفر استدعاء حذف/تعديل في الشفرة مثبت أعلاه.
- **التوافق**: كود قديم/مخطط جديد: يعمل (لا كتابة ممنوعة في الشفرة أصلًا).
  كود جديد/مخطط قديم: يعمل (بلا منع حتى التطبيق — الانكشاف القديم مؤقتًا).
- **الصفوف القائمة**: لا شيء يُفشل الهجرة — المشغّلات لا تمس البيانات.
- **النسخ الاحتياطي**: إلزامي قبل التطبيق (نسخة مُتحقَّق منها + `RUN_GUIDE.md` §9).
- **التراجع**: `Down` يسقط المشغّلات (والدالة في `Postgres`) — آمن، بلا فقدان —
  يُختَبر على نسخة مهملة حصرًا.
- **نصا `SQL`**: `docs/audit/migrations/RF019_{sqlite,postgres}.sql` (مولّدان، للقراءة والمراجعة).

## إجراء تنقية سجلات التدقيق القديمة (الموثق — `BQ-023`)

> الصلاحية: **مشغّل النشر وحده** (منفذ النشر على القاعدة مباشرة). لا زر ولا نقطة
> نهاية في التطبيق عمدًا — أي طلب تنقية عبر التطبيق مرفوض بالتصميم.
> الاحتفاظ: **سنتان** — تُنقَّى الصفوف ذات `Timestamp` الأقدم من سنتين فقط.

1. **الشروط المسبقة** (كلها إلزامية): نسخة احتياطية مُتحقَّق منها (استعادة مُجرَّبة
   على مرحلية) + اعتماد مكتوب من المالك يذكر العتبة الزمنية + نافذة صيانة
   (التنقية خارج أوقات العمل).
2. **الجرد أولًا** (قراءة فقط — تُرفَق بالاعتماد):
   `SELECT COUNT(*) FROM AuditLogs WHERE Timestamp < <العتبة>;`
   وتوابعها في `DocumentFieldChanges` عبر `AuditLogId`.
3. **التنفيذ** (`SQLite`): `DROP TRIGGER IF EXISTS` للمشغّلات الأربعة →
   `DELETE FROM DocumentFieldChanges WHERE AuditLogId IN (SELECT Id FROM AuditLogs WHERE Timestamp < <العتبة>)` →
   `DELETE FROM AuditLogs WHERE Timestamp < <العتبة>` → إعادة إنشاء المشغّلات
   الأربعة بنصوصها الحرفية من ملف الهجرة → `VACUUM` اختياري.
   (`PostgreSQL`): `DROP TRIGGER` الأربعة → الحذفان نفسهما بصيغة `NOW() - INTERVAL '2 years'`
   → إعادة إنشاء المشغّلات (الدالة باقية — لا تُسقَط) → `VACUUM (ANALYZE AuditLogs, DocumentFieldChanges)` اختياري.
4. **التحقق**: إعادة استعلام الجرد (يجب صفرًا فوق العتبة) + دخول تجريبي وإنشاء
   ملف (تدقيق جديد يُكتَب) + محاولة `UPDATE` تجريبية على صف قديم (يجب أن تُرفَض —
   إثبات عودة المنع).
5. **التوثيق**: قيد في سجل النشر (التاريخ، العتبة، الأعداد قبل/بعد، اسم المنفذ،
   نتيجة التحقق) — هذا القيد هو «تدقيق التنقية» (التنقية خارج التطبيق فلا صف تدقيق آلي لها).
