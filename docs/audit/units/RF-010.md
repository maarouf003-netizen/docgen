# `RF-010` — تزامن متفائل `rowversion` للتحرير الطويل والحالة

> الفرع: `refactor/RF-010-concurrency` (من رأس `refactor/RF-015-currency` التراكمي).
> الحالة: موجز مكتوب (Step 2) — بانتظار التنفيذ والتحقق.
> **تنبيه قاعدة 5**: الهجرتان تُكتَبان ولا تُطبَّقان (`dotnet ef database update` محظور)؛ نصا `SQL`
> في `docs/audit/migrations/`؛ ثم STOP لاعتماد صريح منفصل قبل أي تطبيق.
> القرارات المعتمدة لهذه الوحدة: `BQ-033` = رفض الثاني (`409`)؛ `BQ-031` (منع المغلق) **مؤجل**
> لوحدة مستقلة — هذه الوحدة تزامن خالص بلا أي منع جديد.

## Objective

التعارض `409` بدل المحو الصامت: محاميان يحرران نفس الملف (أو يغيران حالته) معًا —
الثاني مرفوض برسالة عربية ودية مع إعادة التحميل، بدل أن يمحو الأخير الأول بصمت.

## Current problem

صفر رموز تزامن في النظام كله (`INT-002` + `INT-012`):
`UpdateAsync` قراءة-تعديل-حفظ بلا إصدار، وفحوص آلة الحالات ذاكرية على قراءة خارج
المعاملة ثم كتابة داخلها بلا قفل — الأخير يربح والوقائع تحفظ الاثنتين.

## Business behavior affected

مرفوض جديد مقصود ومعتمد (`BQ-033`): `409` برسالة عربية عند التعارض
(تحرير أو حالة) — «تغيّر الملف أثناء التحرير من مستخدم آخر — أعد تحميل الملف وحاول مجددًا».
ما عداه none. التوافق: غياب `version` في الطلب = قبول بلا فحص مبكر (لكن الزيادة
والشبكة تنشطان — أي كاتب قديم يزيد العدّاد فيُكشَف لاحقًا) — عملاء قدامى لا ينكسرون.
النوع المخالف للحقل (`string` بدل رقم) يُرفض `400` إطاريًا قبل الوصول للخدمة.

## Security impact

إغلاق فقدان صامت لبيانات قانونية/مالية في نافذة تحرير طويلة؛ لا توسعة سطح
(نفس نقاط النهاية والعقود، حقل إصدار جديد فقط).

   بالنسخة القديمة → اليوم `200` (محو صامت)، وبعد الإصلاح `409`. نفس السيناريو
   للحالة (`status` ثم `status` بالنسخة القديمة — انتقال صالح من الحالتين لعزل
   الإصدار عن الآلة). زيادة العدّاد بعد الحفظ الناجح. اختبارات `RF001*` القائمة

2. توافق: طلب بلا `version` يُقبل (لا كسر للعملاء القدامى)؛ نوع مخالف → `400`.
3. الكاملة خلفية + `oxlint + tsc -b + vitest + build` واجهة على قواعد معزولة.

## Rollback strategy

## تحليلات الهجرة (قاعدة 5)

- **الهجرة**: عمود `Version` (`long`, `IsConcurrencyToken()`) على `Documents` —
  `SQLite`: `INTEGER NOT NULL DEFAULT 0`؛ `Postgres`: `bigint NOT NULL DEFAULT 0`.
  عدّاد تزيده الخدمة عند كل حفظ محمي، وتفحصه `EF` في `WHERE` عند الحفظ
  (محمول — لا توليد مخزني ولا اعتماد `rowversion` الخاص بـ`SQL Server`).
  لا قيد فريد، لا فحص صفوف، لا تحويل بيانات — إضافة خالصة.
- **الأثر**: كتابة فقط عند الحفظ (مقارنة `WHERE RowVersion = @original` + تحديث القيمة) —
  لا قفل طويل، لا هجرة ثقيلة على هذا الحجم (~2000 ملف/سنة)؛ مع ذلك تُطبَّق في نافذة صيانة.
- **التوافق**: كود قديم/مخطط جديد: يعمل (يتجاهل العمود؛ `EF` القديمة لا تفحصه).
  كود جديد/مخطط قديم: يعمل جزئيًا (الفحص المبكر اليدوي يرفض التعارض الواضح حتى بلا
  العمود؛ شبكة السباق `EF` تنشط بعد التطبيق) — دفاع عمق، لا اعتماد أحادي.
- **الصفوف القائمة**: لا شيء يُفشل الهجرة — كل الصفوف تنال القيمة الافتراضية تلقائيًا.
  لا استعلام تنظيف لازم (بخلاف `RF-009`).
- **النسخ الاحتياطي**: إلزامي قبل التطبيق (نسخة مُتحقَّق منها + `RUN_GUIDE.md` §9) —
  قاعدة عامة لكل هجرة، لا خطر خاص هنا.
- **التراجع**: `Down` يُسقط العمود فقط (آمن — لا بيانات عمل beyond العدّادات نفسها)
  — يُختَبر على نسخة مهملة حصرًا. ملاحظة: بعد التراجع يعود السلوك «الأخير يربح»
  — مقبول كتراجع طارئ موثق.
- **الهجرتان**: `20261002133853_RF010_ConcurrencyVersion` (SQLite) و
  `20261002134010_RF010_ConcurrencyVersionPg` (PostgreSQL).
- **نصا `SQL`**: `docs/audit/migrations/RF010_sqlite.sql` (`ALTER TABLE "Documents"
  ADD "Version" INTEGER NOT NULL DEFAULT 0;`) و`RF010_postgres.sql` (`bigint` —
  نفسه) — مولّدان بـ`dotnet ef` ومُراجَعان، للقراءة والمراجعة.
