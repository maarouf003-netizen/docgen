# Runbook — تعطّل الدخول/المصادقة

## الأعراض

- المستخدمون لا يسجلون الدخول: `401`، أو `423` (حساب مقفل)، أو `429` (حد محاولات).
- طلبات مصادَقة تفشل فجأة بـ`401` رغم جلسة سارية.
- `403` مع رسالة CSRF لكل كتابة.

## التشخيص (بالترتيب)

1. **الحساب مقفل؟** `423` + `Lockout:MaxFailedAttempts` — انتظر `Lockout:LockoutMinutes`
   (يتصاعد حتى `MaxLockoutMinutes`) أو أعد تعيين الحساب من الإدارة.
2. **حد محاولات IP؟** `429` + `Retry-After` — انتظر النافذة (`RateLimiting:WindowMinutes`)،
   أو راجع مصدر الطلبات المتكررة.
3. **كل الجلسات سقطت؟** تحقق من تغيير `Jwt__Secret` (تدوير بلا تنسيق يُبطل كل الرموز)
   أو تغيير دور/فرع المستخدم (`TokenVersion`/تحقق الادعاءات).
4. **JWT غير صالح؟** تحقق من `Jwt:Secret` (32 بايت على الأقل)، `Issuer`/`Audience`، وساعة الخادم.
5. **`403` CSRF فقط؟** الكوكي `docgen_csrf` لا يصل (Secure/SameSite خلف بروتوكول غير HTTPS
   بسبب `KnownProxies` غير مضبوط) — راجع [`deploy.md`](deploy.md) و`RUN_GUIDE` §9.
6. **القاعدة؟** `/readyz` — المصادقة تقرأ المستخدم/`LoginAttempts`.

## الإجراء

- لا تعطّل `Jwt`/CSRF للعلاج. أصلح السبب (وكيل/بروتوكول/سر/قفل).
- تدوير سر JWT فقط في نافذة معلنة (كل المستخدمين سيُعاد دخولهم).
- أعد تشغيل نسخة واحدة أولًا وتحقق قبل تعميم الإجراء.

## التحقق

- دخول ناجح بحساب اختباري، `/api/auth/me` يعيد الدور/الفرع الصحيحين.
- كتابة بسيطة (تغيير كلمة مرور) تنجح (CSRF سليم).

## التصعيد

مالك النظام فورًا إذا كان الأثر لكل المستخدمين (>5 دقائق).
