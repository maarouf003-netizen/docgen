# خطة توسع `R0-6` — الدفعتان المستقلتان

> **الحالة:** مسودة بانتظار موافقة المالك — **يُمنع أي تنفيذ قبل الاعتماد الصريح**.
> **الخلفية:** عينة `R0-6` (`PortalController` 9 + `ReviewLettersController` 6) مدموجة في `master` (`PR #23`)
> بقراري المالك الموثقين: شكل `403` المعتمد `{ message }` من المعالج العام، ومستوى سجل رفض النطاق `Warning`.
> **الأساس:** `master @ 6a57678`. الجرد أدناه محقق عليه بأوامر `grep` منفذة (35 موضعًا، كلها نمط صرف).
> **النطاق:** حذف `catch (UnauthorizedAccessException) { return Forbid(); }` فقط — بلا أي مساس بالعقود.

## 2. الدفعة A — `EntityRegistryController` (19)

- **لماذا وحده**: أكبر من العينة كلها (19 مقابل 15)، وعلى السجل المركزي (إنشاء/دمج/توحيد الفروع) —
  دفعة واحدة مع البقية تُصعّب المراجعة وترفع كلفة أي انزلاق.
- **الخطوات (بالترتيب الإلزامي):**
  1. اختبارات عقد تثبت الشكل المعتمد (`403` + جسم `{ message }` غير فارغ) عبر محفزات حتمية
     تبلغ مسار الخدمة الرامي (لا الحراس الاستباقية التي ترد `Forbid` مباشرة):
     رئيس خارج محافظة القيد في عملية فرع، أو دور مصرح يطلب نطاقًا أجنبيًا
     (مثال: دمج/توحيد فرعين من محافظتين، أو إحصاء/إنشاء بقيد خارج النطاق).
  2. تدقيق محتوى الرسائل (خفيف): التأكد أن رسائل `UnauthorizedAccessException` المنبعثة في
     هذه الدفعة وصفية للسياسة ولا تكشف بيانات جديدة — الحالة `403` مقابل `404` قائمة أصلًا
     ولا تتغير، فالفرق إغناء النص فقط. أي مسار يتبين أنه يكشف وجود مورد يُستثنى تمويهًا
     وفق §4.2 ولا يُحذف.
  3. حذف المواضع الـ19: **18 كتلة متطابقة ميكانيكية** + **موضع واحد `catch`-وحيد يتطلب
     فكّ `try`** (`ApproveReview :193` — لا حذف `catch` وحده، بل إزالة `try {`/`}` وإزاحة
     الجسم، وإلا بقي `try` يتيمًا بخطأ `CS1524`. الدرس من `Stats` في العينة
     `REFACTORING_PLAN.md:210`).
  4. البوابات الكاملة (`dotnet test`، و`npx oxlint src`، و`npx tsc -b`، و`npx vitest run`، و`npm run build`).
  5. تحديث تعليق `GlobalExceptionHandler.cs:42-44` («المتحكمات نفسها تحوّله إلى `Forbid()`» —
     لم يعد صحيحًا لهذا المتحكم) وإلحاق سجل الدفعة في `REFACTORING_PLAN.md`.
- **الأثر المتوقع**: صفر واجهة (`client.ts:17` يترجم أي `403` لرسالته الثابتة)؛ السجل `Warning` (مطبق مسبقًا).
- **صراحة العائد (استشاري — تأكيد القصد):** لا تحسين مرئي للمستخدم — الرسالة الخادمية لا تبلغ
  الواجهة أبدًا؛ القيمة اتساق خلفي (شكل `403` موحد لمستهلكي الـAPI) + سجل مركزي بمستوى صحيح فقط.
- **ازدواج شكل `403` داخل النقطة (مقبول صراحة):** الحارس الاستباقي يرد `403` فارغًا
  (`Forbid()` — لا `UseStatusCodePages` في السلسلة) بينما مسار الخدمة يرد `403` بجسم `{ message }`.
  الواجهة تحجب كليهما؛ لا توحيد مطلوب — توثيق قبول فقط.
- **الأثر المتوقع**: صفر واجهة (`client.ts:17` يترجم أي `403` لرسالته الثابتة)؛ السجل `Warning` (مطبق مسبقًا).
- **الفرع المقترح**: `refactor/r06-entityregistry` من `master` ثم `PR` مستقل.
