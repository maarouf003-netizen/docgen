# خطة محكمة: منع حذف ملفٍ فيه إنابة أو استئناف (أي حالة)

> **الحالة:** معتمدة المبدأ والرسائل والنطاق (يشمل المناب) — بانتظار موافقة صريحة على هذه
> الوثيقة قبل أي تنفيذ. لا يُكتب أي كود ولا تُعدَّل أي اختبارات قبل الموافقة.
>
> **مراجعة نقدية (خبير):** رُوجعت مرحلة مرحلة مقابل الكود — سليمة بنيويًا بلا ثغرات حاجبة،
> مع 4 تصحيحات مطبقة أدناه: (F1) تحديث اختبار «فشل الحذف» القائم بدل ادعاء بقائه أخضر،
> (F2) مرتكز المناب هو حالة `isMirror` لا `form.sourceDelegationId` (غير موجود)،
> (F3) تدفق إنشاء الاستئناف تكامليًا مسمّى صراحة، (F4/F5) حالة مشطوب + تصحيح مسار `Repository.cs`.

## 1) الهدف والنطاق

- **الهدف:** منع الحذف المنطقي لأي ملفٍ مرتبط بإنابة (صادرة عنه أو مناب عنها —
  بأي حالة: معلقة/معينة/مسجلة/منفذة) أو باستئناف واحد على الأقل (منظور/محسوم/مشطوب).
- **داخل النطاق:** حارس خلفي في `DeleteAsync` + صدق خطأ الواجهة + تعطيل استباقي
  مريح + اختبارات خلفية/تكاملية/أمامية + التحقق الكامل.
- **خارج النطاق عمدًا:** مسار الاستعادة (`RestoreAsync`)، الحذف المنطقي نفسه،
  الهجرات (لا تغيير مخطط)، ملفات الخطط الأخرى، أي تعديل على قواعد التسطير السابقة.

## 2) القاعدة المعتمدة (نصًا)

يُرفض الحذف عند أول شرط متحقق بهذا الترتيب:

1. `doc.Delegations.Count > 0` (إنابة صادرة، أي حالة) ←
   «لا يمكن حذف الملف المنيب لوجود إنابة صادرة عنه»
2. `doc.SourceDelegationId is not null` (الملف مناب عن إنابة، أي حالة) ←
   «لا يمكن حذف الملف المناب لوجود إنابة مرتبطة به»
3. `(await _appeals.ListByDocumentAsync(doc.Id, ct)).Count > 0` (أي استئناف، أي حالة) ←
   «لا يمكن حذف الملف لوجود استئناف مرتبط به»

## 3) الخلفية — التنفيذ المخطط

### 3-1) الموضع الدقيق

- الملف: `backend/src/DocGenerator.Application/Services/DocumentService.cs`
- الدالة: `DeleteAsync` (تبدأ سطر 315). يُدرج الفحص بعد قراءة `doc` والتحقق من
  `null` (سطر 317-319) و**قبل** `await _tx.RunAsync` (سطر 321) — تحقق قبل تغيير،
  خارج المعاملة، كسائر حراس `UpdateAsync`.

### 3-2) المنطق المخطط (شبه كود — ليس تنفيذًا)

```csharp
// داخل DeleteAsync بعد التأكد من وجود doc:
if (doc.Delegations.Count > 0)
    throw new ArgumentException("لا يمكن حذف الملف المنيب لوجود إنابة صادرة عنه");
if (doc.SourceDelegationId is not null)
    throw new ArgumentException("لا يمكن حذف الملف المناب لوجود إنابة مرتبطة به");
if ((await _appeals.ListByDocumentAsync(doc.Id, ct)).Count > 0)
    throw new ArgumentException("لا يمكن حذف الملف لوجود استئناف مرتبط به");
```

### 3-3) لماذا هذا الشكل (مبررات ملزمة)

- `doc.Delegations` محمّلة أصلًا في `GetByIdAsync` عبر
  `Persistence\Repository.cs:63-68` (`WithIncludes`) — الفحصان الأول والثاني **صفر استعلامات إضافية**.
- لا يوجد تنقل `Document.Appeals` في الكيان (مؤكد بالبحث في
  `Domain/Entities/Document.cs`) — لذا يُعاد استعمال عقد المستودع القائم
  `IAppealRepository.ListByDocumentAsync` (سطر 16) بدل إضافة عقد جديد؛ تُستدعى
  فقط إذا نجح الفحصان السابقان (تقصير الدائرة)، والاستئنافات لكل ملف 0–2 عادةً.
- `ArgumentException` تُترجم `400` مع النص عبر
  `Api/Middleware/GlobalExceptionHandler.cs:35-62`، و`DocumentsController.Delete`
  (`DocumentsController.cs:298-310`) بلا `try/catch` محلي ويعتمد الوسيط —
  **لا تغيير في المتحكمات**.
- سجل التدقيق يُكتب بعد الحفظ فقط — الرفض لا يترك أثر تدقيق (متسق مع حراس التعديل).
- **لا هجرات:** فحص وجود فقط — **لا تنبيه نشر/تطبيق قواعد**.

## 4) الواجهة — التنفيذ المخطط

الحذف من نموذج التعديل فقط (`frontend/src/pages/DocumentForm.tsx`):

### 4-1) إلزامي — صدق الخطأ

- الدالة `deleteDoc` (سطر 639): الـ `catch` الحالي يعرض «فشل الحذف» generic
  (سطر 648) — يُستبدل بعرض `getApiErrorMessage(err)` (مستورد أصلًا سطر 3)
  لتصل رسالة الخلفية الثلاث للمستخدم بدل إخفائها.

### 4-2) مريح — تعطيل استباقي (مفتوح عند الجهل)

- قائمة الإنابات مملوكة أصلًا في النموذج (`delegations` + `delegationsKnown`
  من قفل الحجز) — يُشتق منها `hasLinkedDelegation = delegations.length > 0`
  (أي حالة — ملاحظة: `blocksAssets` هنا **لا** تُستعمل لأن المنع يشمل غير السارية).
- إنابة المناب: حالة `isMirror` القائمة (`DocumentForm.tsx:98`، تُضبط في `:127`
  من `d.sourceDelegationId != null`) — **لا** `form.sourceDelegationId` (غير موجود في
  `form`/`toUpsert`). ملاحظة: `GET .../delegations` يُرجع للمناب إنابته
  (`DocumentDelegationService.cs:290-293`)، أي `delegations.length > 0` يغطي المناب
  أصلًا — فحص `isMirror` تكرار دفاعي حميد يُبقى صراحة.
- الاستئنافات: جلب `GET /documents/{id}/delegations` على نمط الموجود —
  أي `GET /documents/{id}/appeals` في وضع التعديل فقط، بحارس مصفوفة
  (`Array.isArray`) وفشل مفتوح (زر مفعّل، والخلفي يرفض).
- الزر `🗑️ حذف الملف` (سطر ~1205 بعد الإزاحات) يُعطَّل عند العلم المؤكد
  بالارتباط مع ملاحظة `role="note"`: «الملف مرتبط بإنابة/استئناف — الحذف ممنوع».
- `window.confirm` يبقى كما هو للحذف المسموح.

## 5) الاختبارات المخططة

### 5-1) خلفية (نمط البذور القائم — بلا بذور جديدة ثقيلة)

في `backend/tests/DocGenerator.Application.Tests/DocumentDelegationServiceTests.cs`
(أو ملف خدمة المستندات الأنسب عند التنفيذ — يُحسم عندها بلا توسع):

1. حذف ملف بإنابة معلّقة ← رفض بالرسالة 1.
2. حذف ملف بإنابة **منفذة** ← رفض بالرسالة 1 (إثبات «حتى لو لم تكن سارية»).
3. حذف ملف مناب (`SourceDelegationId != null`) ← رفض بالرسالة 2.
4. حذف ملف باستئناف **محسوم** ← رفض بالرسالة 3 (إثبات «حتى لو كان محسوم»).
5. حذف ملف باستئناف منظور ← رفض بالرسالة 3.
6. حذف ملف باستئناف **مشطوب** ← رفض بالرسالة 3 (تغطية «أي حالة» كاملة).
7. حذف ملف نظيف ← نجاح `true` + صف تدقيق `delete`.

### 5-2) تكاملية (`DelegationsIntegrationTests.cs` + تدفق استئناف مسمّى — لا تغطية قائمة للاستئنافات)

1. `DELETE /api/documents/{id}` على ملفٍ بإنابة ← `400` + النص 1 في المحتوى
   (إنشاء الإنابة بنمط البذور القائم في `DelegationsIntegrationTests.cs:22,129`).
2. `DELETE` على ملفٍ باستئناف محسوم ← `400` + النص 3، عبر التدفق الكامل الصريح:
   إنشاء ملف ← `POST documents/{id}/appeals` بتوكن المحامي المالك (الاتجاه + المستأنفون
   + نص القرار — كل الحقول `nullable` في `UpsertAppealRequest`) ← استخراج معرف الاستئناف
   من `201` ← `POST appeals/{id}/decide` (رقم/تاريخ/منطوق/نتيجة) ← `DELETE` الملف.
   (لا مساعد `ApiFactory` للاستئنافات — يُبنى التدفق باستدعاءات HTTP صريحة.)

### 5-3) أمامية (`DocumentForm.payloadAndFields.test.tsx` — قسم الحذف القائم)

1. الزر معطّل + الملاحظة ظاهرة عند إنابة معلومة (محاكاة `.../delegations`).
2. الزر معطّل عند استئناف معلوم (محاكاة `.../appeals`) وعند `isMirror`.
3. رفض خلفي `400` ← نص الرسالة يظهر في صندوق الخطأ (بعد `confirm`).
4. فشل الجلبين ← الزر مفعّل (مفتوح) — الخلفي هو الضامن.
5. **تحديث إلزامي** لاختبار «يعرض «فشل الحذف»…» القائم (`:353`): بعد §4-1 يُرجع
   `getApiErrorMessage(Error('server error'))` رسالة «تعذر الاتصال بالخادم…» لا «فشل الحذف» —
   يُحوَّل ليصبح إثبات صدق الخطأ (رفض `400` مع `message` ← يظهر النص).

### 5-4) عدم كسر

- بذور الحذف القائمة (`ApiFactory.CreateDocumentAsync` بلا إنابات/استئنافات)
  تبقى خضراء (الجلب الجديد يُرجع غير-مصفوفة في المحاكاة القديمة ← `[]` ← مفعّل)،
  **عدا** اختبار «يعرض «فشل الحذف»…» الذي يُحدَّث عمدًا ليصبح إثبات صدق الخطأ (§5-3/5).

## 6) التحقق الإلزامي بعد التنفيذ (بالترتيب)

1. `dotnet build` صفر تحذيرات/أخطاء.
2. `dotnet test` المشروعان (`Application.Tests` كاملًا + `Api.Tests` كاملًا) أخضر.
3. `npx oxlint src` صفر/صفر + `npx tsc -b` نظيف + `npx vitest run` أخضر + `npm run build` ناجح.
4. `grep` بقايا: لا «فشل الحذف» generic في مسار الحذف، ولا رسائل قديمة.
5. مراجعة مسار نهاية-لنهاية: زر معطّل ← تأكيد ← `DELETE` ← `400`+نص ← عرض النص.

## 7) مخاطر موثقة ومقبولة سلفًا

- **R1:** ملف نظيف تُنشأ عليه إنابة/استئناف **بعد** فتح نموذج التعديل وقبل ضغط
  الحذف — الواجهة قد تعرض الزر مفعّلًا؛ الخلفي يرفض لحظتها (نافذة لحظية نادرة،
  مغلقة خلفيًا — نفس فلسفة السباق المقبول سابقًا).
- **R2:** `ListByDocumentAsync` تجلب الكيانات الكاملة لا عدًّا — مقبول للحجم
  (0–2/ملف) وتفاديًا لعقد مستودع جديد؛ يُعاد النظر فقط بدليل أداء فعلي.
- **R3:** الاستعادة (`RestoreAsync`) تبقى بلا قيد عمدًا — الحذف هو الفعل المدمر
  موضوع هذه الخطة.
