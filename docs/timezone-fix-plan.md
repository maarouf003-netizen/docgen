## 2) الحل القياسي المؤكد (نعم — هو الأفضل وفق الأصول)

الحل المركزي (محوّل `ValueConverter<DateTime>` شامل عبر `ConfigureConventions` في السياقين) **هو
التوصية الرسمية حرفيًا**، لا اجتهادًا:

- **توثيق `Microsoft Learn` الرسمي** (`EF Core — Value Conversions`، قسم «Specify the DateTime.Kind
  when reading dates»): «من الشائع تخزين وقت `UTC` دائمًا ثم ضبط العلم بمحوّل قيمة…
  `v => new DateTime(v.Ticks, DateTimeKind.Utc)`»، ويختم: «وَحِّد كل الوصول للقاعدة على `UTC`
  دائمًا، ولا تتعامل مع المحلي إلا عند العرض للمستخدم» — وهذا نص قاعدتنا المقترحة.
- **توثيق `Npgsql` الرسمي** (`Date and Time Handling` + ملاحظات 6.0): `timestamptz` ↔ `DateTime`
  بـ `Kind=Utc`، و«يُوصى بطوابع `UTC` حيث أمكن»، والكتابة بغير `Utc` إلى `timestamptz` **ترمي
  استثناءً** — أي أن المحوّل المركزي يحمي مسار `Postgres` أيضًا من كتابة خاطئة مستقبلًا.
- **توثيق `System.Text.Json` الرسمي**: التسلسل تابع لـ `Kind` (`Utc` ← `Z`، `Unspecified` ← بلا
  إزاحة) — وهو آلية الخلل نفسها، فيُغلقها الضمان المركزي من المنبع.
- **البديلان المرفوضان**: إصلاح أمامي فقط (يترك الداء خلفيًا، ويهدد صيغ `yyyy-MM-dd` النصية بإزاحة
  يوم عند إلحاق `Z` عشوائيًا)، ومحوّل `JSON` وحده (يصلح السلك لا المقارنات داخل الخادم).

## 3) التصميم المعتمد

- **محوّل واحد مشترك** (في `Infrastructure` بجانب الإعدادات) يُطبَّق عبر تجاوز `ConfigureConventions`
  **واحد** في `DocGeneratorDbContext` (القاعدة) فيغطي `DocGeneratorPostgresDbContext` المُشتق تلقائيًا:
  قراءةً `v => new DateTime(v.Ticks, DateTimeKind.Utc)`، وكتابةً: `Utc` كما هو، و`Unspecified`
  ← `SpecifyKind(..., Utc)` (قاعدة المشروع: المخزّن `UTC` دائمًا — سابقة `PortalService.cs:547`)،
  و`Local` ← `ToUniversalTime()`. وتُختبر التغطية صراحةً على `DateTime` **و**`DateTime?` (H3).
- **بلا هجرة (إثبات قاطع)**: المحوّل من النوع نفسه (`DateTime↔DateTime`) فلا يتغير نوع أي عمود —
  ويُثبَت ذلك باختبار صريح `Database.HasPendingModelChanges() == false` على السياقين (H1)،
  وشفاف لترجمة استعلامات `LINQ`.
- **بلا بيانات تاريخية للترحيل**: صفوف `SQLite` الحالية قيم `UTC` أصلًا (كُتبت عبر `UtcNow`) —
  المحوّل يعيد تسميتها صحيحًا؛ وصفوف `Postgres` `Utc` فعلًا (المحوّل محايد عليها).

## 5) الاختبارات المطلوبة (مع التنفيذ — لا الآن)

- ذهاب وعودة `Kind` على `SQLite`: كتابة `UtcNow` ← القراءة `Kind==Utc` وتساوي الـ `Ticks`.
- ذهاب وعودة صريح لـ `DateTime?`: قيمة `null` تبقى `null`، وقيمة `UtcNow` تُقرأ `Kind==Utc` (H3).
- تسلسل القيمة المقروءة ينتهي بـ `Z` (عقد السلك الذي يعتمد عليه `formatDateTime`).
- عقد `/audit-logs`: كل `timestamp` يحمل إزاحة صريحة (H2: اختبار انحدار فقط — لا تعديل كود في
  `DocumentChangeTracker`/`EntityChangeMessages`/`IdempotencyStore`؛ التدقيق الفعلي أثبت أنها
  ليست أعطال عرض: تواريخ تقويمية بصيغة `yyyy-MM-dd`، أو أثر عابر محدود بمهلة `Idempotency`).
- تعميم العقد (مراجعة نقدية ثانية، بعد التنفيذ): اختبار جَوّال يعبر استجابات `/api/documents/{id}`
  و`/api/documents/{id}/changes` كاملةً ويؤكد أن **لا قيمة ISO زمنية (تحوي `T`) بلا `Z`**.
- `HasPendingModelChanges() == false` على السياقين (H1: إثبات «بلا هجرة»).
- `DbLoginRateLimiter.TryRecordFailureAsync` يعمل مع المحوّل (`ExecuteSqlRawAsync` بمعاملات
  `DateTime` — قيد `EF #27534`) (M2).
- بقاء بوابة `Postgres` خضراء (`DOCGEN_TEST_POSTGRES` + `DatabaseInterpreterTests`-النمط القائم)
  مع ثبات نوع التخزين (`timestamptz`)؛ وحدود نوافذ `ServerClock.Now` (`Unspecified`) موثّقة
  كقيد قائم مستقل لا يزعمه الإصلاح (M1/M4).
- إعادة `grep` مواقع الكتابة لحظة التنفيذ (الكود يتغير — التدقيق المبدئي أعلاه لا يغني).
